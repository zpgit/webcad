# The native document and the `.brep` checkpoint

MVP-1's second half: a document format, exact B-Rep serialization through it, two
storage backends, and a model that survives a browser restart. The Worker half is
reported separately in [`MVP-1-WORKER-FINDINGS.md`](MVP-1-WORKER-FINDINGS.md).

**Verdict: persistence is not where time goes, and re-tessellation is.** A 459 kB
checkpoint serializes in 5.0 ms and writes in 1.5 ms; reopening the same document
costs 181 ms, of which 171 ms is re-meshing geometry that was already exact.
IndexedDB beat OPFS on every operation and is now the default on that evidence.
Persistence on the default backend never stalled the main thread past a frame.

Three results were not predicted:

- **The document phases of recovery are cold-start costs, not payload costs.**
  Restoring a 5.9 kB document takes 7.3 ms on a fresh page and 0.24 ms in steady
  state. See [Recovery, in phases](#recovery-in-phases).
- **OPFS is 1.8–45× slower than IndexedDB and stores every document twice**, and
  the gap is widest on the cheapest operation — listing. See
  [IndexedDB versus OPFS](#indexeddb-versus-opfs).
- **A checkpoint's bytes change without its geometry changing**, which rules out
  hashing a payload as a dirty check. See
  [The bytes are not a change detector](#the-bytes-are-not-a-change-detector).

## Build under test

| | |
| --- | --- |
| OCCT | V8_0_1 (reports `8.0.1`), `BinTools` binary B-Rep, format `occt-bin-brep-v4` |
| Emscripten | 6.0.7 |
| Container | schema version 1: `manifest.json`, `features.json`, `geometry.brep` |
| Storage | IndexedDB and OPFS, both implemented, both measured |
| Renderer | three.js 0.185.1, WebGPU and WebGL2 both verified |
| Host | Windows 11, 18 cores, Chrome (system install), headless |

Raw output is in `measurements/document.json` (WebGPU) and
`measurements/document-webgl2.json`, regenerated by `npm run verify:browser`.
Like everything under `measurements/`, they are build products and are not
committed — so the numbers below are the record, and this document is what
survives them. The measurement itself lives in
`tests/browser/document-measurements.ts` and runs against the real kernel, the
real document layer, and both real stores.

**How precise these numbers are, and why it matters for reading them.** The two
artifacts are two runs, not two backends: the host is an ordinary desktop running
an ordinary Chrome alongside the verification, and across the six runs recorded
while developing this, the same 459 kB checkpoint serialized at anywhere from
70 to 112 kB/ms. That spread appears in kernel-side serialization too, which no
renderer can affect, so it is host load rather than a backend difference — do not
read the WebGL2 artifact as a WebGL2 result.

Every figure below comes from `measurements/document.json` unless it says
otherwise, with the second artifact quoted where the spread changes what a reader
should conclude. **Treat ratios and orderings as findings and absolute
milliseconds as ±50%.** Anything that depended on precision finer than that would
not be a result on this machine, and none of the conclusions here do.

## Serialize and restore, against size

Five workloads, chosen so throughput can be read as a function of size rather
than asserted from one point. Medians over 5–9 iterations, measured from the
caller's side with the kernel in its Worker; the last two columns are the same
medians expressed as throughput out of and into the kernel.

| Workload | Bodies | Faces | Payload | Serialize | Restore | Out | In |
| --- | --- | --- | --- | --- | --- | --- | --- |
| One box | 1 | 6 | 3.0 kB | 0.30 ms | 0.28 ms | 10 kB/ms | 11 kB/ms |
| Drilled block (demo scene) | 1 | 7 | 5.2 kB | 0.29 ms | 0.24 ms | 18 kB/ms | 22 kB/ms |
| 12-hole plate | 1 | 17 | 14.5 kB | 0.52 ms | 0.55 ms | 28 kB/ms | 26 kB/ms |
| 8 plates | 8 | 136 | 114.7 kB | 1.56 ms | 2.99 ms | 74 kB/ms | 38 kB/ms |
| 32 plates | 32 | 544 | 458.5 kB | 5.01 ms | 6.26 ms | 92 kB/ms | 73 kB/ms |

**Finding: small checkpoints are latency-bound, large ones are throughput-bound.**
Below about 15 kB the cost is a Worker round trip — roughly 0.3 ms — and the
payload is nearly free. Above 100 kB the fixed cost disappears into the work and
throughput settles at **74–92 kB/ms serializing and 64–73 kB/ms restoring** across
the two committed artifacts, and 70–112 / 46–77 across all six runs. The apparent
9× improvement in "throughput" across the ladder is that fixed cost being
amortized, not the encoder getting faster.

**Finding: restoring is more expensive than serializing above ~100 kB**, by
1.2–1.9×. The direction held in every run and at every size above the 12-hole
plate. Writing a shape is a traversal; reading one builds topology, and the
asymmetry grows with the amount of topology. Both directions are recorded on the
operation log with their payload sizes (`src/kernel/types.ts`), so this stays
measurable without new instrumentation.

The transport is not the story. The artifact records the kernel-side median beside
the caller's, over the same iterations, and the difference for the 458 kB payload
is **0.32 ms out and 0.15 ms in** (0.34 and 0.18 in the other artifact) —
consistent with the Worker stage's 0.1–0.5 ms per operation, and a transfer rather
than a copy in both directions. `npm run verify:browser` fails if a restore
payload was cloned instead of transferred, which is otherwise invisible: the
request still works and merely copies a checkpoint each time.

### What the payload is made of

| Workload | Bytes per face |
| --- | --- |
| One box | 504 B |
| Drilled block | 753 B |
| 12-hole plate | 873 B |
| 8 plates | 864 B |
| 32 plates | 863 B |

**Finding: payload size tracks face count at ~860 bytes per face** for
Boolean-derived topology — 873, 864, and 863 bytes per face across a 31× spread in
payload size. A box is cheaper per face because its faces are planar and its edges
are lines, which is why the smallest workloads sit below the line.

Extrapolating — and this *is* an extrapolation, from nothing bigger than 458 kB —
a 10,000-face model would be about 8.4 MB, roughly 75–120 ms to serialize and
110–185 ms to restore. That would put restoration past a frame and into the same
territory as a Boolean, which is fine while it stays in the Worker and is exactly
the regime MVP-2 needs to measure rather than assume.

The encoding is `occt-bin-brep-v4` (`BinTools_FormatVersion_CURRENT`), written
with `withTriangles=false`: **no mesh is stored**. Confirmed by measurement —
tessellating a body before saving does not change its payload size. Restoration
therefore always re-meshes, which is a deliberate cost this stage wanted to see
rather than hide behind a cached preview. [Recovery](#recovery-in-phases) is
where that decision shows up.

The container costs 1,174 bytes on top of the demo block's 4,718-byte checkpoint —
20% of the 5,892-byte document — for a manifest with provenance, integrity, and an
identity mapping, plus a five-entry construction record. Both grow slowly and
linearly: one identity per body in the manifest, one line per operation in the
record. It is 20% at the smallest document that exists and a rounding error at any
size worth measuring.

### The bytes are not a change detector

Serializing an untouched body twice is byte-identical. **Tessellating it in
between flips 6 bytes in a 6,567-byte payload — one per face** — in OCCT's
per-shape housekeeping flags, which the stream carries. Geometry, size, and the
restored result are unaffected.

So a payload hash cannot serve as a dirty check, and cannot serve as a document
dedup key: a document that was merely *displayed* would hash differently from the
same document unopened. The spec puts its determinism requirement on identities
and the construction record for exactly this reason. The CRC-32 in the manifest is
integrity for a specific stored payload, which this does not affect.

## IndexedDB versus OPFS

The architecture note poses this as an open question, so both backends were
implemented and neither was called the default until measured. Same document,
same parts, same iteration count; medians over 5 iterations.

| Operation | IndexedDB 5.6 kB | OPFS 5.6 kB | IndexedDB 459 kB | OPFS 459 kB |
| --- | --- | --- | --- | --- |
| Save (all parts, atomically) | **0.60 ms** | 9.99 ms | **1.55 ms** | 12.06 ms |
| Read (all parts) | **0.23 ms** | 6.46 ms | **1.15 ms** | 7.21 ms |
| Open (read + verify + restore) | **0.48 ms** | 6.35 ms | **9.58 ms** | 17.12 ms |
| List documents | **0.24 ms** | 10.65 ms | **0.41 ms** | 10.77 ms |
| Delete | **0.70 ms** | 1.93 ms | **0.63 ms** | 1.95 ms |

**Finding: IndexedDB wins every operation, by 1.8× to 45×**, and the ordering held
in every run. The 1.8× is the one case where the gap nearly closes — opening a
large document, where the kernel's restore dominates both backends equally. On
everything the store itself does it is 2.8–45×. It is also the gentler curve: an
80× increase in payload costs it 2.6× on save, which works out to ~297 kB/ms of
write throughput at 459 kB.

**Finding: OPFS's cost is per-file, not per-byte.** Saving 5.6 kB costs 9.99 ms
and saving 459 kB costs 12.06 ms — 80× the data for 21% more time. Four file
handles are the price, and the payload rides along nearly free. That also explains
the worst ratio in the table: **listing documents costs OPFS 10.7 ms against
IndexedDB's 0.41 ms**, because a list is directory enumeration plus one summary
file per document, while IndexedDB answers it from one object store. Both figures
are for five stored documents, and OPFS's grows with that count in units of a file
read while IndexedDB's grows in units of a cursor step. The document list is UI:
10.7 ms is most of a frame spent before anything is drawn, and it is the operation
a user triggers most often.

### The decision

**Default: IndexedDB** (`src/storage/index.ts`). Faster on every operation,
cheaper to list, and it stores each document once. It also gets atomicity from a
`readwrite` transaction rather than from a scheme this codebase had to invent.

**What OPFS cost, and it is not only time.** `FileSystemHandle.move()` is not
defined for directories, so the design's "write to a temp directory and swap it
in" was not implementable. The OPFS backend instead keeps **two generations plus
a commit marker**: a save writes into whichever of `a`/`b` is not current and
writes `summary.json` last with a sequence number; the readable generation is
whichever has the highest readable sequence. It is correct — an interrupted save
leaves a generation with no summary, so the previous one still wins, and the
conformance suite asserts this against both a first save and an overwrite — but
**every document is stored twice**. Against IndexedDB's single copy, that is a 2×
footprint for a backend that is also slower.

**What would change the choice.** Two things, both MVP-2's to answer, which is
why `OpfsStore` stays in the tree rather than being deleted:

1. **Checkpoints large enough that one IndexedDB value is the problem.** IndexedDB
   takes a payload as a single value and structured-clones it; OPFS can write a
   stream. At tens of megabytes the fixed-cost advantage inverts into a
   memory-pressure disadvantage.
2. **Moving persistence into the Worker.** OPFS's synchronous access handles
   (`createSyncAccessHandle`) are Worker-only, and they are the fast path this
   measurement never touched. The main-thread OPFS API is the slow one, and that
   is what these numbers describe.

### What was not exercised

**IndexedDB quota exhaustion.** Chrome does not enforce
`Storage.overrideQuotaForOrigin` for IndexedDB: an 8 MB save succeeds under a
1 MB quota. The same override stops OPFS dead. Retried on a fresh browser context
with the override applied before any storage was touched, in case the bucket's
limit had been cached — same result. So the typed quota failure is proven for
OPFS in a real browser and for IndexedDB only by a Node test that maps the
exception. `npm run verify:storage` reports this as a skip with its reason and
lists it again under "Not exercised" after the verdict.

There is an irony worth stating plainly: **the default backend is the one whose
quota behavior cannot be provoked.** A user who fills their disk will meet a code
path that has never run in a browser.

## Recovery, in phases

The number MVP-1 exists to produce. Measured across a genuine reload against a
stored document, with each phase timed where it happens — from outside, reading,
restoring, and re-tessellating are one `await`. The document is the demo drilled
block: 5.9 kB, one body, 160 triangles.

| Phase | Dev server (WebGPU) | Production build | Dev server (WebGL2) |
| --- | --- | --- | --- |
| Kernel ready (WASM + OCCT init) | 499.6 ms | 233.4 ms | 200.9 ms |
| Document read from storage | 0.6 ms | 0.4 ms | 0.6 ms |
| Checkpoint restore | 7.3 ms | 6.8 ms | 9.5 ms |
| Re-tessellate and upload | 39.6 ms | 28.4 ms | 44.7 ms |
| First frame | 17.0 ms | 30.5 ms | 45.3 ms |
| Unattributed (module load, viewport init) | 19.6 ms | 2.5 ms | 3.2 ms |
| **Total, load to geometry on screen** | **583.8 ms** | **302.0 ms** | **304.2 ms** |

The build column is read from the built app's own `performance` entries during
`npm run verify:dist`, which prints them rather than writing an artifact. That it
can be read at all is the point: the instrumentation ships, so these are phases of
what a user runs rather than of a dev server.

**Finding: recovery is dominated by kernel startup, which the document layer
cannot improve.** 86% of the dev-server total, 77% of the build's, and 66% of the
WebGL2 run's is WASM instantiation and OCCT initialization — the previous stage's
cost, reported separately for exactly this reason. Everything the document format
does, from reading storage to geometry uploaded, is **36–55 ms**.

**Finding: the document phases are cold-start costs, not payload costs.**
Restoring this 5.9 kB checkpoint takes 7.3 ms during recovery and 0.24 ms in
steady state — a factor of 30. Re-tessellating 160 triangles takes 39.6 ms during
recovery, against roughly 5 ms per body once a session is warm. Both are OCCT
initializing machinery on first use — the same effect that made MVP-0 report a
66 ms Boolean that costs 9 ms warm. The practical consequence: **for MVP-1-size
documents, recovery is roughly constant at ~50 ms regardless of what is in the
document**, and only the largest workloads measured here would exceed it.

**Finding: re-tessellation is the dominant document-side cost of opening, by an
order of magnitude.** For the 459 kB, 32-body document, a full open costs 181 ms,
of which 9.6 ms is storage plus restore and **171 ms is re-meshing** — about 5.3 ms
per body, 18× everything else put together. This is the price of the design
decision not to persist a preview mesh, and it is now a number rather than an
intuition. Persisting meshes would trade document size and a staleness problem for
most of that 171 ms; nothing here forces the trade, but MVP-2 should make it
knowingly rather than inherit it.

The first-frame column should be read against the idle frame interval, which is
**33.3 ms in headless Chrome** — it composites lazily. A 17.0 ms first frame is
half a frame interval and the WebGL2 run's 45.3 ms is 1.4 of them; across runs the
same phase has ranged from 5.9 to 45.4 ms for identical geometry. None of that is
evidence about upload speed, only about when the compositor next came round. The
phase is recorded only if a frame actually arrives, so an unmeasured phase never
reads as an instant one.

Phases are recorded as `performance.measure` entries named `webcad:*`
(`src/app/timing.ts`), unconditionally rather than under a dev flag. They ship, so
the table's build column is a measurement of what users run, and a phase
breakdown shows up in a DevTools profile next to the frames it explains.
`npm run verify:dist` asserts the entries exist in the build.

## The main thread during persistence

The design's open question: the container's checksum and JSON encoding run on the
main thread, and the kernel was moved off it precisely so long operations cannot
freeze the viewport. Measured with the same self-rescheduling 4 ms timer probe the
Worker stage used, on the 459 kB document.

| Probe | Iterations | Worst stall | Median | Samples |
| --- | --- | --- | --- | --- |
| Idle baseline | — | 6.0 ms | 4.6 ms | 30 |
| Restore only, 458 kB into the Worker | 8 | 6.5 ms | 4.3 ms | 12 |
| IndexedDB save (build + write) | 12 | 6.5 ms | 4.7 ms | 18 |
| IndexedDB open (read + restore + tessellate) | 4 | 6.5 ms | 4.6 ms | 153 |
| OPFS save (build + write) | 12 | 5.4 ms | 4.3 ms | 61 |
| OPFS open (read + restore + tessellate) | 4 | 6.6 ms | 4.6 ms | 177 |

**Finding: persistence on the default backend never stalled the main thread past a
frame.** In this artifact the worst stall anywhere is 6.6 ms against an idle
baseline of 6.0 ms, and one frame is 16.7 ms. The restore-only probe is the one
that answers the Worker spec's requirement directly, with no storage or mesher in
the window: **sending a 458 kB checkpoint into the Worker and restoring it eight
times costs the main thread nothing measurable above idle.**

**Finding: OPFS crossed a frame and IndexedDB never did.** Across the six runs
recorded while developing this, IndexedDB's worst stall was 8.2 ms — always inside
a frame — while OPFS exceeded one frame in three of them, at 12.0 and 17.9 ms on a
save and 19.2 and 19.6 ms on an open. Nothing approached three frames. This is a
second, independent argument for the backend choice, and it is the kind of thing a
single run would have hidden in either direction: the committed artifact above
shows OPFS at 5.4 ms.

`npm run verify:browser` fails if any of these exceeds three frames, and reports a
finding with the payload size that produced it if one exceeds a single frame — so
this is a checked bound rather than a described one, and the OPFS crossings above
were reported by the run rather than noticed by a reader.

Decomposing a 459 kB IndexedDB save, which costs 8.1 ms end to end: **5.0 ms is
the kernel serializing** (in the Worker), **1.5 ms is the write**, and the
remaining **~1.6 ms is CRC-32 and JSON encoding on the main thread**. Take that
last figure as an upper bound rather than a measurement — it is a residual between
medians taken under different load, and in the other artifact it comes out at
approximately zero. The stall probe bounds it independently and more soundly: the
longest synchronous block anywhere in a burst of twelve saves was 6.5 ms against a
6.0 ms idle baseline, and the checksum is one such block.

The main-thread share is small but it is the part that scales linearly with
payload: at 8 MB it would be roughly 25 ms, past a frame. That is the trigger for
moving the checksum into the Worker, and there is no reason to do it before then.

A note on why the probe runs a burst: a single save is faster than the probe's own
4 ms period, so it yields no samples at all — which is an *absent* responsiveness
result, not a passing one. Twelve saves in one window give the probe something to
sample without changing what it reports, since a save that blocked the main thread
would block it once per iteration.

## Payload-size impact

Serialization needed no new OCCT toolkit: `BinTools` lives in `TKBRep`, already
linked. The artifact still grew, because previously dead-stripped code became
reachable. Measured by building the facade at HEAD and with the change, back to
back:

| | Before | After | Delta |
| --- | --- | --- | --- |
| `webcad_kernel.wasm` | 7,098,776 B | 7,216,979 B | +118 kB (+1.67%) |
| `.wasm`, brotli | 2,011,079 B | 2,035,066 B | +24 kB (+1.19%) |
| Loader `.mjs` | 85,354 B | 105,212 B | +20 kB (+23%) |
| Loader, brotli | 21,069 B | 25,151 B | +4 kB (+19%) |

**Finding: exact B-Rep persistence costs 24 kB brotli in the kernel artifact.**
Against a 2.0 MB compressed kernel, that is not a cost worth discussing.

The loader grew proportionally more than the kernel, which is `register_vector`
pulling in embind's vector machinery for one list of integers. Worth remembering
if the loader's size ever matters; it does not at 25 kB.

## Two things that read like bugs and are not

**A reopened body reports a different bounding box.** `BRepBndLib::Add` uses a
face's triangulation when it has one, so a displayed body's box is inflated by
roughly the mesh deflection — 0.0457 on the demo block — while a restored,
not-yet-meshed body reports the exact extents to 1e-7. **The restored body is the
accurate one.** Nothing may assert bounding-box equality across a save and open,
and fit-to-view frames a reopened document very slightly tighter than it framed
the same document before saving.

**OCCT writes its own diagnostics to the console on a bad payload**, e.g.
`BinTools_ShapeSet::Read: File was not written with this version of the
topology`. The typed error propagates correctly and the refusal path works: the
message is OCCT printing through the Emscripten module's console output, beside
the application's own message rather than instead of it. A run that exercises a
damaged payload should expect it and not read it as a defect.

## What this does not answer

- **Nothing about large models.** The largest checkpoint measured is 458.5 kB
  across 544 faces, and it was built by multiplying one plate rather than by
  modelling something real. Every extrapolation above is labelled as one. STEP-file
  scale is MVP-2's.
- **Nothing about STEP.** Saving does not pass geometry through an interchange
  schema, and no STEP import or export exists to compare against. The document is
  explicitly not STEP.
- **Nothing about recompute.** The construction record is inert: written, read
  back, and displayed, never executed. Restoration comes from the checkpoint
  alone. Replay needs stable references to faces and edges across topology
  changes, which is MVP-4's whole subject.
- **Nothing about a second browser.** Chrome only, one machine, headless, with
  SwiftShader standing in for a GPU. OPFS and IndexedDB behave differently across
  engines, and Safari in particular has its own OPFS story.
- **Nothing about concurrent tabs.** Two tabs on the same origin share both
  stores and the last-opened record. Neither backend was measured or reasoned
  about under a second writer.
- **Nothing about quota for the default backend**, as above.
- **Nothing about documents at rest over time.** No migration has been performed:
  schema version 1 is the only version that has ever existed, and the refusal path
  for an unknown one is tested but has never met a real future document.
- **Nothing about the Worker-side OPFS fast path**, which is the one measurement
  that could reverse the storage decision.

## Reproducing

```bash
npm run kernel:build          # once
npm test                      # 114 tests
npm run verify:browser        # WebGPU + serialization, storage, recovery
npm run verify:browser:webgl  # WebGL2 fallback
npm run verify:storage        # storage conformance, both backends
npm run verify:dist           # the built app, including save/reload/reopen
```

Artifacts land in `measurements/`: `document.json` and `document-webgl2.json` for
everything above, `worker.json` for the boundary, `payload.json` for artifact
size, plus viewport screenshots.
