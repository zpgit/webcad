# Moving the kernel into a Worker

MVP-0's most consequential result was that the main thread was already blocked on
trivial geometry, and its recommendation was to move the kernel into a Worker
before the native document format was designed
([`MVP-0-FINDINGS.md`](MVP-0-FINDINGS.md)). This is what that move cost and what
it bought.

**Verdict: the main thread is free, and the boundary is cheap.** A 160 ms
Boolean stalls the main thread for 6.5 ms, against a 5.5 ms stall when the
kernel is doing nothing at all. Steady-state transport overhead is 0.1–0.5 ms
per operation. Nothing here argues for shared memory.

Two findings were not predicted, and both change what the next stage should
assume. See [Two corrections to MVP-0](#two-corrections-to-mvp-0).

## Main-thread responsiveness

The question MVP-0 raised. Measured by a self-rescheduling 4 ms timer running
while a kernel operation is in flight: a blocked main thread cannot service it,
so a synchronous 156 ms call would appear as one 156 ms gap.

| Probe | Wall clock | Worst stall | Median | Samples |
| --- | --- | --- | --- | --- |
| Idle baseline (kernel doing nothing) | 151.6 ms | 5.5 ms | 4.5 ms | 32 |
| Oblique Boolean (tilted cylinder through a large one) | 159.9 ms | 6.5 ms | 4.7 ms | 31 |
| Fine tessellation (r=80, 0.002 deflection) | 156.7 ms | 12.8 ms | 5.0 ms | 30 |

**Finding: the kernel no longer blocks anything.** The Boolean's worst stall is
6.5 ms against an idle baseline of 5.5 ms — one millisecond of difference across
160 ms of geometry work. The baseline is what makes that readable: without it,
6.5 ms could have been the kernel's shadow instead of the timer's own scheduling
noise.

The fine tessellation's 12.8 ms is the one number above the baseline, and it is
real work rather than blocking: the main thread receives a 181 kB mesh and hands
it to the GPU. Still inside one frame, and it is proportional to mesh size
rather than to the 157 ms the kernel spent. WebGL2 gives the same picture, so
this is not a backend artifact.

Nine frames of geometry work, zero frames of freeze. That is the whole point of
the change, and it is now asserted by `npm run verify:browser` rather than
claimed here — the run fails if a stall exceeds three frames.

What did not change: the user still waits 160 ms. Latency is unchanged; only
its effect on the UI is. The readout says so in those terms now, which is why
the old "⚠ over frame budget" flag was replaced by "⏱ 9× frame latency" rather
than deleted. Relabelling a real cost would have been the one dishonest way to
make the warning disappear.

## Transport cost

Every operation records both its kernel-side duration and the caller's round
trip. The difference is what the boundary costs.

| Operation | Kernel | Round trip | Transport |
| --- | --- | --- | --- |
| `createBox` (first after init) | 24.60 ms | 27.45 ms | 2.86 ms |
| `createCylinder` | 4.25 ms | 4.51 ms | 0.27 ms |
| `subtract` | 72.22 ms | 72.44 ms | 0.22 ms |
| `tessellate` (5024 triangles) | 18.90 ms | 19.35 ms | 0.45 ms |
| `release` | 0.22 ms | 0.48 ms | 0.26 ms |
| `bodyInfo` | 0.02 ms | 0.23 ms | 0.21 ms |

**Finding: 0.1–0.5 ms per operation in steady state**, against operations
costing tens of milliseconds. The boundary is not where time goes.

Two outliers are worth naming rather than averaging away.

The first `createBox` after initialization pays 2.9 ms. That is the Worker
finishing its own warm-up, not a per-call cost; it happens once.

One `bodyInfo` recorded 27.9 ms of transport against 0.1 ms of kernel time.
Nothing was wrong with the Worker: the main thread was busy decoding a
screenshot when the response arrived, and a response cannot be delivered to a
thread that is not listening. **Transport time as measured includes main-thread
scheduling delay**, which means it is a measure of the whole trip and not of the
Worker. That is the right thing to measure for latency, but it will look bad
whenever the main thread is doing something else, and readers of these numbers
should not attribute it to the transport.

## Mesh transfer

The one cost MVP-0 named in advance: mesh crossed as views over WASM memory with
no copy, and a Worker forces a copy into a transferable buffer
(`MVP-0-FINDINGS.md:67-72`).

Copying out of the WASM heap, inside the Worker:

| Triangles | Bytes | Copy |
| --- | --- | --- |
| 12 | 720 B | 0.015 ms |
| 160 | 6.0 kB | 0.020 ms |
| 5024 | 181 kB | 0.120 ms |

**Finding: the copy is 0.12 ms for a 181 kB mesh** — under 0.1% of the 157 ms
tessellation that produced it. It was worth measuring; it is not worth
optimizing.

### Transferables versus structured cloning

The design predicted a net-neutral copy count and left open whether transferring
actually beats cloning at these sizes. Measured with an echo Worker, per
round trip:

| Payload | Transfer | Structured clone |
| --- | --- | --- |
| 720 B (12 triangles) | 0.072 ms | **0.059 ms** |
| 181 kB (5024 triangles) | **0.156 ms** | 0.211 ms |

**Finding: transferring is slower for small meshes and faster for large ones.**
The direction was the same in all three runs recorded while developing this
(WebGPU twice, WebGL2 once); the magnitude was not. At 181 kB, transfer beat
cloning by between 1.35× and 3.9× depending on the run, so treat the ratio as
"faster" rather than as a number. At 720 B, cloning won every time, by about
0.013 ms.

Below roughly a few kilobytes the fixed cost of detaching three buffers exceeds
the cost of just copying them. This is worth stating plainly, because the change
was built on the assumption that transferring is the better choice: at MVP-0
mesh sizes that assumption is **wrong**, by an amount far too small to matter.
It is already right at 181 kB, and MVP-2 meshes will be larger still, which is
why the machinery stays.

### The copy count

The design predicted the total copy count would not change — one copy either
way, relocated from the main thread into the Worker:

| | MVP-0 | Now |
| --- | --- | --- |
| WASM heap → JS | view, no copy | 0.12 ms copy, in the Worker |
| postMessage | — | transfer, no copy |
| JS → `BufferAttribute` | one copy | none, buffer adopted |

**Finding: the prediction held.** The viewport adopts the transferred arrays
directly (`src/viewport/viewport.ts`), so the copy it used to make is gone and
the one the Worker makes replaces it. This only holds because the viewport was
changed to adopt; had it kept copying, the change would have added a copy rather
than moved one, and the numbers above would have said so.

## Two corrections to MVP-0

**MVP-0's Boolean timings included one-time OCCT setup.** A drilled block
measured 66–73 ms there, and still does as the first Boolean of a session. The
second identical Boolean costs **9 ms**. The 66 ms was mostly OCCT initializing
its Boolean machinery on first use, not the cost of the operation.

This does not weaken MVP-0's conclusion — the first Boolean genuinely blocked
four frames, and a fine tessellation is genuinely 137 ms with no warm-up excuse.
But it does mean "a two-primitive Boolean takes four frames" describes a cold
kernel, and the steady-state figure is half a frame. Later stages should treat
MVP-0's operation table as cold-start numbers. It is also why the responsiveness
probes here use an oblique cut through a large cylinder rather than the demo
scene's drilled block: the drilled block is no longer slow enough to prove
anything.

**Headless Chrome throttles timers and fires almost no animation frames.** The
first responsiveness probe used `requestAnimationFrame` and observed two frames
in 140 ms, which is indistinguishable from a completely blocked main thread. Any
future measurement of main-thread behavior needs
`--disable-background-timer-throttling` and friends, which
`scripts/verify-browser.mjs` now passes. A rAF-based probe would have reported a
catastrophic failure that was not happening.

## What this does not answer

- **Nothing about shared memory.** It stays closed, as
  `MVP-0-FINDINGS.md:74-75` required — plain message passing was measured and
  was not found wanting. Revisit only if a future stage produces a boundary cost
  that matters, which 0.5 ms per operation is not.
- **Nothing about parallelism.** One Worker, one operation at a time. A second
  Worker would need a second OCCT instance and a story for sharing handles
  between them; nothing yet needs it.
- **Nothing about cancellation.** A long operation cannot be aborted. The main
  thread stays responsive during it, which makes this less urgent than it was,
  but a user who starts a slow Boolean by mistake still waits it out.
- **Nothing about large models.** These meshes top out at 5024 triangles. The
  transfer curve is flat and the clone curve is linear, so the crossover is
  established, but absolute costs at STEP-file scale belong to MVP-2.
- **Nothing about the production build.** Verified in `vite dev` and confirmed
  that `vite build` emits the Worker as its own chunk resolving the Emscripten
  module correctly. The built `dist/` does not ship `webcad_kernel.wasm` at all,
  which predates this change and is tracked separately.

## Reproducing

```bash
npm run kernel:build          # once
npm test                      # 66 tests
npm run verify:browser        # WebGPU + boundary measurements
npm run verify:browser:webgl  # WebGL2 fallback
```

Artifacts land in `measurements/`: `worker.json`, `worker-webgl2.json`,
`browser.json`, `browser-webgl2.json`, and viewport screenshots.
