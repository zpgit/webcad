### Notes from group 1, for the findings document

- **No new toolkit.** `BinTools` is `src/ModelingData/TKBRep/BinTools` in V8_0_1 — already linked. `native/CMakeLists.txt` is unchanged.
- **The payload grew anyway**, because previously dead-stripped code is now reachable. Measured by building the facade at HEAD and with the change, back to back: wasm 7,098,776 → 7,216,979 raw (+118 kB, +1.67%) and 2,011,079 → 2,035,066 brotli (+24 kB, +1.19%). The **loader grew proportionally more** — 85,354 → 105,212 raw (+23%), 21,069 → 25,151 brotli (+19%) — which is `register_vector` pulling in embind's vector machinery for one list of integers. Worth revisiting if the loader's size ever matters; it does not at 25 kB.
- **The encoding is `occt-bin-brep-v4`** (`BinTools_FormatVersion_CURRENT`), written with `withTriangles=false`. Confirmed by measurement: tessellating a body before saving does not change its payload size.
- **A checkpoint's bytes are not a change detector.** Serializing an untouched body twice is byte-identical, but tessellating it in between flips 6 bytes in a 6567-byte payload — one per face — in OCCT's per-shape housekeeping flags, which the stream carries. Geometry, size, and the restored result are unaffected. This rules out hashing the payload as a dirty check or as a document-dedup key, and the spec's determinism requirement is on identities and the construction record for exactly this kind of reason.
- **Restore skips `BRepCheck_Analyzer`** deliberately: creation already validated the geometry, and a full validity analysis over every body lands on the recovery-time measurement this stage exists to take. Restore still refuses a body with no solid.
- Verified against the raw module by `native/build/smoke-serialize.mjs` (scratch, gitignored) pending the real suite in 2.6: exact volume, area, topology counts, validity, closedness, and analytic surface types preserved for a drilled block and a cylinder; restored bodies tessellate and take part in Booleans; unknown handle, truncated, garbage, and unstaged payloads all fail typed with no handles issued and the kernel still usable. The existing 66 tests are unaffected.

## 2. Kernel boundary and protocol (TypeScript)

- [x] 2.1 Add `serialize` and `restore` request kinds and their result shapes to `src/kernel/worker/protocol.ts`, including the inbound payload and the outbound payload with its encoding, byte length, and writing OCCT version.
- [x] 2.2 Implement both in `src/kernel/worker/handler.ts`: copy the serialized bytes out of WASM memory into an owned buffer for transfer out, and copy an inbound payload into WASM memory before restoring. Never retain a view over WASM memory across either call.
- [x] 2.3 Teach the transports to carry transferables *into* the Worker (`worker-transport.ts`), and make the in-process transport (`transport.ts`) match that ownership behavior so tests exercise the same discipline rather than a laxer one.
- [x] 2.4 Add `serialize(bodyIds)` and `restore(payload)` to `src/kernel/kernel.ts`, transferring the inbound buffer and documenting that the caller loses ownership of it.
- [x] 2.5 Record payload byte counts on the operation-log entry for both directions (`src/kernel/types.ts` `OperationRecord`), so checkpoint size can be related to the time spent on it.
- [x] 2.6 Tests (`tests/serialization.test.ts`, Node, in-process transport): round-trip exactness — volume, area, face/edge/vertex/solid counts, validity, closedness, and face-type summary preserved for a box, a cylinder, and a drilled block; order preserved across multiple bodies; a restored body usable as a Boolean operand; truncated, garbage, and empty payloads failing with typed errors and leaving the live-handle count unchanged; and no handle leak across a serialize/restore/release cycle.

### Notes from group 2, for the findings document

- **The transfer list is derived, not assembled.** `requestTransferables(request)` in `protocol.ts` is the single place that answers "what moves with this request", and both transports call it. A caller cannot add a payload and forget to transfer it.
- **The in-process transport now structured-clones requests that carry transferables.** Without it the Node suite would exercise a laxer contract than the one that ships: the handler would receive the caller's own array and the caller would still hold a usable reference. The "restoring detaches the caller's buffer" test passes only because of this, and would silently pass for the wrong reason otherwise. Requests with nothing to transfer are untouched, so the cost falls only on `restore`.
- **`bodyInfo().boundingBox` depends on whether a body has been tessellated**, and a restored body reports a *different* box than the same body did before saving. Not a serialization defect — `BRepBndLib::Add` uses a face's triangulation when it has one, so a displayed body's box is inflated by roughly the mesh deflection (0.0457 on the demo block) while a restored, not-yet-meshed body reports the exact extents to 1e-7. **Consequences for later groups:** nothing may assert bbox equality across a save/open, and fit-to-view will frame a reopened document very slightly tighter than it framed the same document before saving. Worth stating plainly in the findings, because "the bounding box changed after reopening" reads like a bug and is not one.
- **OCCT writes its own diagnostics to the console on a bad payload** — `BinTools_ShapeSet::Read: File was not written with this version of the topology`. The typed error still propagates correctly, but group 3's refusal path should expect this noise in the browser console alongside its own message, and group 6 should not treat it as a console error that fails a run.
- **Size datapoint:** the demo drilled block is a 4718-byte checkpoint.
- `npm run verify:browser` now proves the round trip across a real Worker: geometry, analytic surfaces, and exact extents preserved, and it **fails if the payload was cloned rather than transferred** — a missing transfer list is otherwise invisible, since the request still works and merely copies a checkpoint each time. This is the one mechanism the Node suite structurally cannot prove.
- Gate at the end of group 2: `typecheck` clean, **87 tests pass** (66 before, +21), `verify:browser` and `verify:dist` both pass.

### Notes from group 3, for the findings document

- **Parts are `Record<PartName, Uint8Array>`, named for the architecture note's layout** (`manifest.json`, `features.json`, `geometry.brep`). Uniformly bytes so a store can persist them without knowing which are text: the OPFS backend gets file names for free, IndexedDB gets record fields, and a byte-identical round trip is assertable. `topology.bin` and `preview.glb` from the note's layout are deliberately absent — there is no identity mapping to write yet, and a persisted preview would hide re-tessellation from the recovery measurement.
- **CRC-32, not `crypto.subtle`.** `subtle` is undefined outside a secure context, so a page served over plain http could not save at all — an absurd way to lose someone's geometry, and a worse failure than the weaker hash. The threat here is a torn write or a truncated read, not a forged document, and the length is checked independently. Same reasoning drove `crypto.getRandomValues` over `crypto.randomUUID` for document ids, which is also secure-context only.
- **`nextBodyOrdinal` has to be persisted, not derived.** Deriving the next identity from the surviving body count means a document whose `b1` was deleted mints `b2` a second time on reopening, silently aliasing two different bodies in its own history. Tested directly.
- **The order of checks on the way in is the safety argument**, and is tested as such: schema version, then part presence, then integrity, and only then does the kernel see a byte. Two tests pin it — an unknown schema version wins over a malformed manifest (the user needs "upgrade the app", not "your file is broken"), and a truncated payload is refused with `restoreCalls === 0`.
- **`readDocument` consumes the geometry part**, because restoring transfers it into the kernel. Asserted against the real kernel rather than only documented: a store that cached the parts it handed over would otherwise find them hollow on a second read, far from the cause.
- **The document/kernel seam is a three-method interface** (`DocumentKernel`: serialize, restore, release, plus `occtVersion`). That is what makes the refusal paths testable without WASM — a checkpoint that disagrees with its own manifest is not something real OCCT will produce on request, and 20 of the 23 tests run in milliseconds against a fake.
- **Constraint worth recording: Node's type stripping is strip-only and rejects TypeScript parameter properties.** `tsc` accepts them, so this passes typecheck and then fails the entire test file at load. Cost a round trip in group 3; the kernel's errors happened to avoid the shorthand already. Anything under `src/` that tests import must assign fields in the constructor body.
- Gate at the end of group 3: `typecheck` clean, **110 tests pass** (87 before, +23).

### Notes from group 4, for the findings document

- **Listing metadata is supplied at save time, not read back out of the manifest.** The store must not interpret parts, and listing must not touch a checkpoint; deriving a summary by parsing `manifest.json` would violate the first to satisfy the second. So `save(summary, parts)` takes both, and the summary is stored separately. A conformance check asserts a listed summary carries exactly four metadata keys and no bytes.
- **IndexedDB gets atomicity from a transaction; OPFS had to be given it.** `FileSystemHandle.move()` is not defined for directories and is not universally available, so the "write to a temp directory and swap" plan from the design was not implementable as written. The scheme instead is **two generations plus a commit marker**: a save writes into whichever of `a`/`b` is not current and writes `summary.json` last, carrying a sequence number; the readable generation is whichever has the highest readable sequence. An interrupted save leaves a generation with no summary, so the previous one still wins. **Cost: each document is stored twice.** Bounded at 2×, and worth stating in the findings since it doubles OPFS's footprint against IndexedDB's.
- **Both backends now write the summary last.** IndexedDB does not need it — the transaction is what commits — but keeping the order identical means one failure story rather than two, and it is what makes a mid-save fault land mid-save on both.
- **Fault injection needed no production seam.** Both backends read `parts[name]` one at a time, so a parts object with a throwing property getter fails them exactly where a real failure would, through the real code path. Nothing was added to `src/` for a test's benefit — worth preferring over the `onBeforeCommit` hook the design was heading toward.
- **Chrome does not enforce `Storage.overrideQuotaForOrigin` for IndexedDB.** An 8 MB save succeeds under a 1 MB quota; the same override stops OPFS dead. Retried on a fresh browser context with the override applied before any storage was touched, in case the bucket's limit had been cached — same result. So **IndexedDB quota exhaustion is not exercised anywhere**, and the run says so: reported as a skip with the reason, listed again under "Not exercised" after the verdict, and the exception-to-typed-failure mapping covered by a Node test instead. A run that printed PASSED while quietly not having tried something would be the worse outcome.
- **The storage run waits for `domcontentloaded`, not `load`.** It needs an origin to scope storage to and a module graph to import from, not a started application — waiting for the kernel and the viewport made a storage check depend on a renderer it never touches, and cost a 30-second timeout on the first attempt.
- **Default backend is IndexedDB, provisionally.** Chosen because its atomicity is a transaction rather than a scheme this codebase had to invent, which makes it the safer thing to be wrong about. Task 6.4 revisits it on the measurements; nothing above `src/storage/index.ts` knows which backend is in use.
- Gate at the end of group 4: `typecheck` clean, **114 Node tests pass** (110 before), and **24 conformance checks pass — 12 against each backend**, with identical observable behavior.

### Notes from group 5, for the findings document

- **`open()` restores before it tears down.** The document is read and its geometry restored into the kernel *first*; only on success are the outgoing bodies released and the viewport cleared. That ordering is what makes "a refusal leaves the session exactly as it was" true rather than aspirational — a user who tries to open a damaged file must not lose the model they already had. The cost is that both documents' geometry is resident for a moment, which is the right trade at MVP-1 sizes and worth revisiting when MVP-2 supplies large ones.
- **Boolean operand identities are captured before the operation runs.** Afterwards the operands are released, and the record refers to bodies by identity rather than by handle — so reading them after the fact would find nothing.
- **`save()` takes one timestamp and uses it for both the manifest and the listing**, so the document and the document list cannot disagree about when it was written.
- **The store measures what it wrote.** `save()` now takes a `DocumentSummaryInput` with no `byteLength` at all, rather than a caller-supplied number the store silently overwrote. A listed size cannot drift from what is actually stored, and a caller cannot be wrong about it.
- **Storage failing to open is reported, not fatal.** A browser that refuses storage still runs the modeller, with the Save button disabled and the reason on screen. Refusing to start would be the wrong trade — persistence is a feature, not a precondition.
- **Verification is end-to-end and includes a real reload**, which is the one thing nothing else in the suite can do: every other check proves the pieces work within a single page's lifetime, which is exactly what a restart invalidates. The run now saves, reloads the browser, waits for restoration, and asserts that **each body comes back under the same identity** — not merely that a body of the same size came back — with exact volume and face count, a re-tessellated mesh on screen, and the construction record intact. Measured on the demo drilled block: **5.8 kB saved, 1 body, 5 history entries, 160 triangles re-tessellated, identity `b3` preserved.**
- **No Node unit tests for `ModelingSession`.** It is glue over `Kernel`, `Viewport`, and `DocumentDraft`, all of which are tested; the behavior worth asserting about the glue is the reload, which needs a browser. Stated so the absence reads as a decision rather than an oversight.
- Gate at the end of group 5: `typecheck` clean, **114 Node tests pass**, `verify:browser` passes including the reload round trip, `verify:storage` passes on both backends, `verify:dist` passes.
